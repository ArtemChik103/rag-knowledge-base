# Логика решения: RAG-система поиска по базе знаний

Данный документ описывает архитектурную модель, компоненты и принципы работы поискового сервиса по корпоративной базе знаний.

---

## 1. Назначение системы

Сервис решает задачу точного извлечения информации из регламентов, инструкций и текстовых документов компании.
Система выполняет три основные функции:
1. Загрузка и структурирование документов форматов PDF, TXT и Markdown.
2. Преобразование текста во фрагменты (чанки) и расчет векторных представлений (эмбеддингов).
3. Семантический поиск релевантных фрагментов по запросу пользователя и синтез точного ответа с указанием первоисточника.

---

## 2. Архитектура сервиса

Система построена по трехзвенной архитектуре:

```
[Пользовательский интерфейс (React / Tailwind)]
                 │
                 ▼  REST API (HTTP / JSON)
[Бэкенд-сервис (FastAPI)]
   ├── Модуль парсинга (DocumentParser)
   ├── Модуль разбиения (RecursiveTextSplitter)
   ├── Векторное хранилище (ChromaDB VectorStore)
   └── Модуль синтеза (RAGEngine)
                 │
                 ▼
[Векторная база данных ChromaDB (HNSW Cosine Index)]
```

### 2.1. Компоненты системы

- **DocumentParser (`backend/document_parser.py`)**:
  - Извлекает текст из файлов PDF, TXT и Markdown.
  - Сохраняет соответствие между текстом и номером страницы документа.
  - Удаляет избыточные пустые строки и нормализует пробельные символы.

- **RecursiveTextSplitter (`backend/text_splitter.py`)**:
  - Делит документ на логические фрагменты заданного размера (500 символов) с перекрытием (100 символов).
  - Учитывает естественные границы текста: абзацы, предложения, пробелы.
  - Формирует метаданные для каждого фрагмента: идентификатор документа, номер страницы, порядковый индекс чанка, начальное и конечное смещение.

- **VectorStore (`backend/vector_store.py`)**:
  - Управляет постоянным хранилищем векторов на базе ChromaDB.
  - Вычисляет 384-мерные плотные векторы через мультиязычную модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`.
  - Выполняет поиск ближайших соседей по косинусному расстоянию (HNSW-индекс).
  - Поддерживает фильтрацию по идентификаторам документов, удаление записей и сброс коллекции.

- **RAGEngine (`backend/rag_engine.py`)**:
  - Координирует этапы индексации и поиска.
  - Принимает текстовый запрос, выполняет векторизацию и поиск Top-K фрагментов.
  - Проверяет порог релевантности (порог косинусного сходства).
  - Формирует структурированный ответ с цитированием страниц и точных цитат из регламента.

- **FastAPI Сервер (`backend/main.py`)**:
  - Предоставляет REST API для загрузки файлов, выполнения поисковых запросов и управления документами.
  - Раздает собранный статический фронтенд.

- **Пользовательский интерфейс (`frontend/`)**:
  - Обеспечивает интерактивную загрузку файлов через Drag-and-Drop.
  - Отображает список проиндексированных документов и состав их чанков.
  - Предоставляет поисковую строку с быстрыми шаблонами вопросов.
  - Показывает сгенерированный ответ, метрики задержки поиска и карточки цитат со страницами.

## 3. Поток обработки данных

### 3.1. Этап индексации (Ingestion Pipeline)

1. Пользователь передает файл через веб-интерфейс или API `POST /api/documents/upload`.
2. Сервер сохраняет файл в директорию `uploaded_docs/`.
3. `DocumentParser` считывает содержимое файла и формирует структуру `ParsedDocument`.
4. `RecursiveTextSplitter` разбивает текст на блоки фиксированного размера с сохранением номеров страниц.
5. `VectorStore` рассчитывает эмбеддинги для каждого блока и сохраняет их в коллекцию ChromaDB.
6. Сервер возвращает клиенту метаданные документа: количество страниц, объем символов и число созданных чанков.

### 3.2. Этап поиска и генерации (Query Pipeline)

1. Пользователь отправляет запрос через API `POST /api/query`.
2. `VectorStore` преобразует текст запроса в вектор той же размерности (384).
3. ChromaDB выполняет поиск $K$ ближайших векторов по метрике косинусного расстояния.
4. Вычисляется оценка сходства (Similarity Score) в диапазоне от 0.0 до 1.0.
5. `RAGEngine` фильтрует фрагменты с низкой релевантностью.
6. Модуль генерации извлекает фактологические фрагменты и формирует итоговый ответ.
7. Ответ обогащается цитатами (название файла, страница, индекс чанка, текст фрагмента) и метриками задержки.

## 4. Обоснование выбора технологий

| Задача | Выбранный инструмент | Причина выбора |
|---|---|---|
| Векторная база данных | ChromaDB | Локальное хранение, поддержка HNSW, отсутствие необходимости в сторонних СУБД |
| Модель эмбеддингов | `paraphrase-multilingual-MiniLM-L12-v2` | Высокая точность для русского и английского языков при компактном размере (470 МБ) |
| Бэкенд-фреймворк | FastAPI + Uvicorn | Асинхронная обработка, строгая валидация Pydantic, автоматическая OpenAPI-документация |
| Обработка PDF | PyPDF / PyMuPDF | Надежное извлечение текста с разбивкой по страницам |
| Фронтенд | React + Vite + Tailwind CSS | Высокая скорость отклика, чистый минималистичный интерфейс без избыточных зависимостей |
